# Realtek `3274:9011` Match-on-Chip Protocol & Quirk Notes

Hardware ID: `3274:9011 Generic Realtek USB2.0 Finger Print Bridge`  
Tested Platform: MECHREVO Wujie 14 (2026, Intel Core Ultra 200V Lunar Lake)

## Protocol Family

Although Windows distributes this device under a `MicroarrayMocWbdi` INF wrapper, USB wire captures confirm that it speaks the **Realtek Match-on-Chip (`realtek`)** bulk protocol rather than `mafpmoc`:

- **USB Endpoints**: Bulk `0x01` OUT (host commands) and Bulk `0x82` IN (responses/status), with no vendor control transfers.
- **Command Header**: Fixed 12-byte structure (`offset 0` = direction/flags `0x05` / `0x45` / `0x85`, `offset 1` = opcode, `offset 10..11` = little-endian uint16 payload length).
- **On-Chip Matching**: Raw fingerprint images never cross the USB bus. The maximum payload is the 350-byte template metadata table (`10` slots × `35` bytes).
- **Core Opcodes**: `05 05`, `45 06`, `45 08`, `45 0e`, `45 22`, `85 21`, `05 07` (cancel capture), and `05 11` (post-verify template update).

## Firmware Divergences on `3274:9011`

Compared to `3274:9003` and `0bda:5816`, the `3274:9011` firmware requires seven device-specific behaviors (isolated behind `FP_RTK_QUIRK_*` flags in the patch):

1. **Template Table Status (`FP_RTK_QUIRK_NO_TEMPLATE_STATUS`)**  
   Template table reads (`co_get_template`) do not follow the standard trailing zero-status check used on older variants, and an empty template database returns `0` records cleanly rather than `FP_DEVICE_ERROR_DATA_FULL`.
2. **Subfactor Normalization (`FP_RTK_QUIRK_NORMALIZE_SUBFACTOR`)**  
   Enrollment commits on `3274:9011` write subfactor byte `0xf7` (`SUB_FINGER_9011`) instead of `0xff` (`SUB_FINGER_01`). When reading stored records back into `FpPrint` objects, `0xf7` is normalized to `SUB_FINGER_01` so `libfprint` metadata validation succeeds.
3. **Explicit Capture Purpose & Mode (`FP_RTK_QUIRK_CAPTURE_PARAMS`)**  
   Capture start (`co_start_capture`), finish poll (`co_finish_capture`), feature identification (`nor_identify_feature`), and cancel (`co_cancel_capture`) require explicit purpose/mode bytes (`mode = 2` during enrollment, `mode = 1` during verification).
4. **12-Sample Enrollment (`FP_RTK_QUIRK_EXACT_ENROLL_STAGES`)**  
   The firmware expects 12 accepted sample stages (`ENROLL_SAMPLES_9011 = 12`) before final enrollment commit.
5. **75 ms Capture Polling Cadence (`FP_RTK_QUIRK_CAPTURE_POLL_DELAY`)**  
   Unthrottled tight polling disrupts capture acquisition; matching the 75 ms polling interval stabilizes sensor state transitions.
6. **Press-and-Release Capture Status Semantics (`FP_RTK_QUIRK_CAPTURE_STATUS`)**  
   In the 5-byte `co_finish_capture` response (`uint8 status` + `int32_le metric`):
   - `00 00 00 00 00` (`metric == 0`) or `metric == -9`: sensor is idle; continue polling.
   - `byte[0] == 0x01` with `metric > 0`: finger is currently held down on the sensor; report `FP_FINGER_STATUS_PRESENT` and continue polling (treating this state as complete causes a single press to be counted multiple times).
   - `byte[0] == 0x00` with `metric > 0`: finger press-and-release sample acquisition is complete; advance the state machine to sample evaluation.
7. **Optional Post-Match Template Update (`FP_RTK_QUIRK_OPTIONAL_UPDATE_STATUS`)**  
   After a successful verification match, `05 11` (`co_update_template`) may return `01 f7 ff ff ff` (`status_detail == -9`), indicating that no self-learning template update was applied. Treating this as a non-fatal no-op prevents verification from aborting after a valid match.

## USB Autosuspend Exclusion

`3274:9011` is added to `denylist_id_table` in `libfprint/fprint-list-udev-hwdb.c` so `udev-hwdb` does not enable `ID_AUTOSUSPEND=1` on this bridge, avoiding USB port-reset glitches when waking the sensor at lock-screen prompt time.
